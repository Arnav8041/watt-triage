# v1 scope boundary

WattTriage v1 was scoped against a two-day build window. The following were considered and
deliberately left out, and their absence should be read as a decision rather than an
omission.

- **API authentication.** Invisible to a demo, adds a header to every call. A shared-secret
  header read from an env var is the intended first addition.
- **Server-sent events / websockets.** The dashboard polls every two seconds, which is
  indistinguishable from push at human timescales. SSE is the intended second addition.
- **A migration runner.** v1 has a single `schema.sql` applied at startup. Migrations
  arrive when there is something to migrate.
- **A scheduler for the retention job.** Rollup and deletion run behind
  `POST /admin/rollup`. In production a cron would call that endpoint; building the cron
  would add no capability the endpoint lacks, and a manual trigger is better for a demo.
- **A separate worker process.** The agent runs in a FastAPI background task. A process
  restart strands `pending` candidates; they remain visible in the database and can be
  re-run. A queue table with `SELECT ... FOR UPDATE SKIP LOCKED` is the intended path to
  crash-safety.
- **Real measured data.** Readings are synthetic, generated by a scripted simulator, and
  the README says so plainly. Real appliance-level datasets (UK-DALE, REDD) were
  considered and rejected: a Rated Breach cannot occur in a recording of a working house,
  so the project's most important scenario would have had to be injected regardless.
